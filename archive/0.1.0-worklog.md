# 0.1.0 worklog

Goal: generate a SIRDS from a height map with simple noise, then recover the
height map and the base pattern from the pixels alone, with node tests as the
proof. Final state: see `0.1.0-plan.md` for what the implementation is; this
file records how it got there and what the numbers actually are.

## step 0 — plan review before writing code

The inherited plan was sound in outline (port the forward model, reverse by
winner-take-all block matching, recover the pattern from a rebuilt link table)
but several of its claims were assumptions, not measurements. Before touching
the implementation I prototyped the whole pipeline in `/tmp` (throwaway, ~200
lines) and measured. Four claims changed:

1. "residual > 0 flags depth edges and seams" — true, but the seam influence
   is much wider than "within 2 px". Low-confidence rate inside vs outside a
   band around a depth discontinuity: 97.4% vs 6.4% at 2 px, 32.1% vs 0.0% at
   12 px, and recovery outside a ~15 px band is 100% exact. The plan's seam test
   now states the band width instead of a 2 px distance.
2. "left to right, first sample wins, holes left empty" for the pattern strip
   — with all recovered links recorded the strip was only 91.6% valid, because
   the border bands contribute wrong-but-noisy links that punch holes in the
   chains. Recording only confident links: 100% valid, 100% correct. This is
   now rule 2 of the reverse section.
3. Nothing in the plan covered the fact that every multiple of the true
   separation also scores residual 0. Found while scanning for degenerate
   parameter settings: with P=100, depthScale=60, a z=1 half-plane scores 0 at
   both s=40 and s=80. Tie-breaking towards the larger s silently returns 80.
   This is now rule 1 of the reverse section and test case 10.
4. The plan's window-size numbers (winX 2 vs 4) were not measured. A sweep
   showed winX=4 dominates winX=2 on every preset, and winX=1 is unusable
   (83.9% exact among "confident" pixels vs 100% for winX>=4). Default kept at
   4; the table lives in `experiments/logs/accuracy-baseline.md`.

Everything else in the plan held up and was implemented as written.

## step 1 — sirds.js

Forward model ported literally from `vendor/gf-source.html` (white noise path
only, no animation), same `hashNoise`, same `same[]` sweep, same pairing.

Reverse: per row, per separation, one column-pair SAD pass over the vertical
window, then a sliding horizontal window. The first version of that had two
bugs that a naive-reference comparison caught immediately: it wrote
`best[x0] = sum` unconditionally (losing the smallest-s tie-break) and
computed `x1` with `+ floor(s/2)` instead of `- floor(s/2)`. After the fix the
incremental matcher is bit-identical to the naive quadruple loop on all four
presets (test 9) and 5x faster.

## step 2 — tests

`tests/run.js` computes ground truth from the documented formula and contains
its own naive matcher, so a change to the forward model cannot silently agree
with itself. Ten cases, 17 checks, all green.

Three test bugs worth recording, all of the same shape — the reference was
wrong, not the implementation:

- `zFromS -> sFromZ` did not invert for 19 of 21 separations. Cause: float
  error on the dyadic rationals of the 8-bit grid. Fixed with a 1e-9 nudge in
  `sFromZ` (see the findings file).
- The naive reference never initialised `resMap` for pixels outside the
  vertical window, so it reported residual 0 where the implementation reported
  "unevaluable", and a strict `!==` on a Float32-vs-Float64 value flagged
  every one of them. Fixed with `resMap.fill(1)` and a 1e-6 tolerance.
- The "distance to a depth edge" helper seeded the distance transform on the
  *different*-value pixels, which makes every pixel's own value a seed and the
  distance 0 everywhere. The correct construction is one distance field per
  distinct value (distance to the nearest pixel holding that value) and then
  the min over all other values.

## step 3 — index.html

All five views, file:// only, no build, no worker. Two bugs that only a
non-browser check could find, both in the element-id map: `showParams` read
`el.Pv` and `buildHeight` wrote `el.depthCv` before either was in the map, so
the page threw on load. Running the inline script under a `node:vm` DOM stub
surfaced both in seconds.

Two real logic bugs fixed at the same time, both of which would have produced
plausible-looking but wrong output:

- an uploaded image was still being compared against the ground truth of the
  previously generated one, so the "reverse-only" path reported metrics for a
  completely different picture;
- "re-generate from recovered" compared the regenerated stereogram against the
  buffer it had just overwritten, which is 100% identical by construction. It
  now compares against a copy taken at generation time: 97.0% of samples
  reproduce exactly, the rest being the masked seams and the unencoded border.

Visual check: rendered the five views to PNG from node (zlib-only encoder) and
looked at them. The recovered map matches the input for flat, shapes, ramp and
torus; the error map is black except along depth discontinuities. The torus
exposed a presentation problem no metric had caught — a binary low-confidence
overlay paints the whole ramp red even though 97.8% of those pixels are
recovered within one step, so the overlay is now a continuous residual tint.

## step 4 — baselines

`node experiments/accuracy.js` sweeps presets, match window, noise grain, and
period/depth combinations at 640 x 400 and rewrites
`experiments/logs/accuracy-baseline.md`. Headline numbers at the defaults
(confident pixels are 100% exact on every preset):

	flat    exact 100.0%  confident 100.0%  z MAE 0.0000
	shapes  exact  98.4%  confident  95.2%  z MAE 0.0094
	torus   exact  90.8%  confident  76.8%  z MAE 0.0115
	ramp    exact  96.3%  confident  77.9%  z MAE 0.0024

Reverse time 105-154 ms at 640 x 400, generation ~10 ms.

Worth knowing from the sweeps: noise grain is the parameter that actually
breaks the reverse (noiseScale=16 drops exact recovery to 37% while
"confident" stays at 98.7%, i.e. the confidence signal correctly stops
trusting the pixels); a larger match window keeps helping on shapes but starts
hurting on smooth gradients, where it blurs the ramp; and everything degrades
gracefully as depthScale grows, down to ~490 ms worst case at P=160,
depthScale=80.

## next step suggestion

0.1.1: attack the smooth-gradient case, which is the weakest part of the
result (torus 90.8% exact, 76.8% confident). The confidence map is already
correct there — the failure is ambiguity between neighbouring separations, not
detection. Two cheap candidates, in order of expected value: (a) a vertical
regularization pass, a row median over a 3-5 row window on the s map, which
costs nothing and should convert most of the remaining torus error; (b)
left-right consistency, rejecting an s whose pair does not agree with the pair
implied by its neighbour. Keep the exact-match invariant and the
smallest-s tie-break intact, and re-measure with the same sweep so the change
is visible in the baseline table.
